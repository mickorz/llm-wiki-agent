## 二、核心发现

### 2.1 Precision 大幅提升（51.5% → 70.7%）

Published 从 97 降到 82，但匹配覆盖的 published 唯一数 58 条，Strict Precision 提升 19.2%。原因：
- Normalize "不要合并触发+收分"指令导致 LLM 更谨慎，normalized 从 217 降到 169
- Dedup 合并更彻底（169→82，合并率 51.5% vs Run 10 的 55.3%）
- 结果：published 更精炼，与 golden 的匹配密度更高

### 2.2 Recall 下降：9 条未匹配，8 条来自番型体系

| Golden ID | 标题 | 根因 |

| GOLDEN-041 | 天胡地胡不计自摸 | 自摸体系规则缺漏（结算阶段未拆出独立条目） |
| GOLDEN-051 | 基础番型互斥取最高 | 番型体系整体缺漏 |
| GOLDEN-052 | 金钩钓与碰碰胡互斥 | 番型体系整体缺漏 |
| GOLDEN-053 | 清一色可叠加 | 番型体系整体缺漏 |

| GOLDEN-057 | 七对F03结构 | 番型体系整体缺漏 |
| GOLDEN-060 | 金钩钓F06结构 | 番型体系整体缺漏 |

### 2.3 番型体系缺漏根因分析

Topic "胡牌判定与番型体系" 产出 35 条 candidates，但经过流水线后，番型结构规则全部丢失：

1. **Discovery 阶段**：35 条 candidates 包含番型信息，但可能过于笼统（如"番型体系包括F01-F11"一条大需求）
2. **Validation 阶段**：可能将细粒度番型规则标记为 derived（7 条 derived 仅占少量）
3. **Normalize 阶段**：原子化拆分不彻底，番型结构规则被压缩进配置或结算条目
4. **Dedup 阶段**：番型细节被合并进 REQ-CONFIG-016（番型开关与倍数下拉配置）和 REQ-SETTLEMENT-020（结算流水线6步）

Published 中与番型相关的条目：
- REQ-CONFIG-016：番型开关与倍数下拉配置（仅配置视角，不含结构规则）
- REQ-SETTLEMENT-020：结算流水线6步（仅提及"确定基础番型"，无具体规则）

## 三、后续优化建议

### P0: 番型体系 Discovery Prompt 强化（最高优先）

在 buildDiscoveryPrompt 中为"胡牌判定与番型体系"topic 增加专项指令：
- 要求逐条提取 F01-F11 每个番型的结构、倍数、互斥关系
- 要求提取根数计算规则
- 要求提取叠加番型名规则
- 强调：每个 F0X 番型应为独立条目，不要合并为一条概述

### P1: Normalize 原子化指令强化

当前"不要合并触发+收分"指令导致 normalized 减少，说明 LLM 理解偏差。改为：
- "每个 F0X 番型的结构定义、倍数、互斥关系应分别拆分为独立条目"
- "番型的触发条件和结算规则应分开记录"

### P2: Dedup 保护番型细节

在 Dedup prompt 中增加：
- "不同 F0X 编号的番型不可合并"
- "互斥规则与番型结构定义不可合并"

### P3: 稳定性验证

重跑 Run 12 验证优化效果，目标：
- Recall ≥ 95%（92/96）
- Strict Precision ≥ 75%
- Published 85-100 条
