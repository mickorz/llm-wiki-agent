可以。结合你现在的 `llm-wiki + opencode-dynamic-workflows`，我建议把这次“Wiki → 需求点”本身做成一个标准 Workflow，后面所有项目都能复用。

核心链路定成：

```text
Raw 原始需求
   ↓
LLM-Wiki
   ↓
候选 Requirement
   ↓
Raw Evidence Validation
   ↓
原子化 / 去重 / 合并
   ↓
Human Checkpoint
   ↓
正式 Requirements
   ↓
Eval
```

## 一、开发优先级

| 优先级 | 要做什么                          | 目标                                    |
| --- | ----------------------------- | ------------------------------------- |
| P0  | 跑通 3 个 Concept 的完整流程          | 验证方案可行                                |
| P0  | Candidate Requirement 提取      | Wiki → 候选需求                           |
| P0  | Raw 证据核查                      | 防止 Wiki 幻觉                            |
| P0  | Requirement Schema            | 固定最小结构                                |
| P0  | 去重 / 合并                       | 避免 Concept 重复                         |
| P0  | checkpoint 人工审核               | 正式入库前确认                               |
| P0  | requirements.jsonl + index.md | 给后续 Agent 使用                          |
| P1  | check/assert                  | 文件存在、source 存在等确定性检查                  |
| P1  | 自动分类                          | UI / gameplay / config / settlement 等 |
| P1  | Traceability Graph            | Raw → Wiki → Requirement              |
| P1  | Eval                          | Precision / Recall / Duplicate 等      |
| P2  | 全量 Wiki 并行转换                  | 扩展整个项目                                |
| P2  | Incremental Update            | Raw 修改只更新受影响需求                        |
| P2  | Requirement → Design Workflow | 接下一阶段概要设计                             |

# 四、Phase 1：Requirement Discovery

这一阶段只负责：

> 找需求，不判断最终正确与否。

而且建议并行。

你的 dynamic workflow 可以采用这种结构。

下面是**目标 Workflow 伪代码**，具体 API 名称按你现在插件已有能力调整：

```js
phase("Requirement Discovery")

const topics = [
  "wiki/concepts/杠与杠分.md",
  "wiki/concepts/荒庄与查叫.md",
  "wiki/concepts/自摸相关规则.md",
]

const candidateResults = await parallel(
  topics.map(topic =>
    agent(`
      你是 Requirement Discovery Agent。

      输入：
      ${topic}

      任务：
      1. 阅读 Concept
      2. 阅读关联 Syntheses
      3. 找出所有候选需求
      4. 每个需求必须原子化
      5. 不做代码设计
      6. 不补充 Wiki 中不存在的规则
      7. 保存 source references

      输出 JSONL。
    `)
  )
)
```

这里千万不要：

```text
一个 Agent
读取整个 Wiki
输出几百个 Requirement
```

还是你之前遇到的“大上下文 + 大 JSON”问题。

应该：

```text
Topic A ─┐
Topic B ─┼→ Parallel
Topic C ─┘
```

# 五、Candidate Requirement Schema

P0 先极简：

```json

  "temp_id": "CAND-001",
  "category": "settlement",
  "title": "杠牌后计算杠分",
  "requirement": "玩家完成符合条件的杠牌后需要计算杠分",
  "wiki_sources": [

  ],
  "raw_source_hints": [

```

注意这里叫：

```text
CAND-xxx
```

不要直接：

```text
REQ-xxx
```

因为它还没有通过验证。

# 六、Phase 2：Evidence Validation

这是整个 Workflow 最重要的一层。

每一个 Candidate：

```text
Candidate Requirement
       ↓
查 raw
       ↓
找到证据
       ↓
判断证据等级
```

建议并行：

```js
phase("Evidence Validation")

const validated = await parallel(
  candidates.map(candidate =>
    agent(`
      验证候选需求：

      ${candidate}

      必须回到 raw 原始需求文档查找依据。

      返回：

      evidence_level:
      - explicit
      - derived
      - unsupported
      - conflict

      同时返回：
      - raw_sources
      - evidence_summary
      - confidence

      禁止仅凭 Wiki 判定需求成立。
    `)
  )
)
```

结果：

```json
{
  "temp_id": "CAND-001",
  "evidence_level": "explicit",
  "raw_sources": [
    "raw/06-结算.md#杠分"
  ],
  "confidence": 0.96
}
```

# 七、这里要正确使用 verify

你之前已经确定过：

> `verify()` 用于 LLM / 语义质量验证。

这里刚好非常适合。

比如验证：

```text
候选 Requirement 的描述
是否真的被 Raw 原文支持？
```

可以：

```js
const result = await verify({
  requirement: candidate.requirement,
  evidence: rawEvidence,
  criteria: `
    Requirement 必须能够从原始文档得到直接支持，
    不允许增加新的游戏规则。
  `
})
```

但不要用 `verify()` 判断：

```text
文件存不存在
JSON 是否生成
requirements.jsonl 是否为空
路径是否正确
```

这些以后应该走你计划增加的：

```text
check/assert
```

职责保持：

```text
agent
    做工作

check/assert
    确定性校验

verify
    LLM 语义校验

checkpoint
    人工判断
```

这套分工非常适合现在这个 Requirement Workflow。

# 八、Phase 3：Atomicity Normalize

验证通过之后，不马上入库。

还需要做：

```text
原子化
+
统一表达
+
统一分类
```

比如发现：

```text
玩家胡牌以后计算番型并进行结算然后显示结算界面
```

应该拆成：

```text
REQ-xxx
计算胡牌番型

REQ-xxx
根据番型计算结算结果

REQ-xxx
结算完成后展示结算界面
```

Normalize Agent 的职责明确限制为：

```text
允许：
拆分
标准化
分类

禁止：
新增业务含义
删除原始约束
修改游戏规则
```

# 九、Phase 4：Semantic Dedup

这是 Wiki 场景必须有的。

因为：



```text

        ↓

        ↓

        ↓
Merge
```

```json

  "id": "REQ-SETTLEMENT-001",

    "raw/06-结算.md"

```

不要删除来源。

应该：

> **合并 Requirement，保留所有 Traceability。**

# 十、Phase 5：Checkpoint

这一层我建议一定保留。

Workflow 到这里停止：

```text

conflict        2
```

然后：

```text
checkpoint(
  "请审核 Requirement Extraction Result"

```

给人查看：


```text

Edit
```

只有：

```text

```

才能进入正式 Requirement。

这也正好对应你之前准备给 dynamic-workflows 增加的 Human-in-the-loop 节点。

```json
  "category": "settlement",

  "evidence_level": "explicit",

    "wiki": [
      "wiki/concepts/杠与杠分.md"

      "raw/06-结算.md"
```

# 十二、Phase 7：Eval

第一版本必须做 Eval，否则你不知道 LLM-Wiki 到底有没有提升需求抽取质量。

第一版人工整理 20～50 条：

```text
golden/requirements.jsonl
```

然后测：

```text
LLM-Wiki → Requirement
```

对 Golden Set。

重点指标：

| 指标                      | 含义                            |
| ----------------------- | ----------------------------- |
| Recall                  | 已知需求找出来多少                     |
| Precision               | 生成的需求有多少是真的                   |
| Unsupported Rate        | 幻觉需求比例                        |
| Duplicate Rate          | 重复需求比例                        |
| Atomicity               | 是否是一条一个行为                     |
| Traceability            | 是否能回溯到 Raw                    |
| Classification Accuracy | UI / Config / Gameplay 分类是否正确 |

我建议 P0 最关注：

```text
Recall
Precision
Unsupported Rate
Traceability
```

不要一开始追十几个指标。

# 十四、失败处理不要写成大量嵌套 if

这点尤其适合你现在正在改的 dynamic workflow。

你之前不喜欢这种：

```js
if (...) {
  if (...) {
    if (...) {
    }
  }
}
```

Requirement Workflow 可以改成“状态驱动”：

```js
phase("Discovery")
const discovery = await runDiscovery()

assert(discovery.outputExists)

phase("Validation")
const validation = await validateEvidence(discovery)

if (validation.hasBlockingError) {
  jump("Report")
}

phase("Normalize")
const normalized = await normalize(validation)

phase("Dedup")
const requirements = await dedup(normalized)

phase("Review")
await checkpoint(requirements)

phase("Publish")
await publish(requirements)

phase("Eval")
await evaluate(requirements)

phase("Report")
await generateReport()
```

未来你的 Composite Control Flow 完成以后，可以进一步变成：

```text
sequence
    ↓
parallel
    ↓
check
    ↓
verify
    ↓
checkpoint
    ↓
jump
```

这个需求抽取 Workflow 其实非常适合作为你 `opencode-dynamic-workflows` 新版控制流能力的第一个真实 Demo。
